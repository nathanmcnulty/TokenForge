# Practical runner and workstation design

Proposed design and next implementation goal, 2026-10-24 UTC. Design only: no code, workflow, credential, infrastructure or publication change is authorized by this document.

## Recommendation

Use **one short GitHub-hosted Linux job for public metadata health**, and keep **account-bound, deep or long discovery on Nathan's workstation**. Reuse TokenForge's existing SQLite stores, evidence schemas, bounded collectors and reports. Do not build a dedicated runner, custom control plane or signed-plan delivery system for this need.

Nathan is the sole trusted administrator and controls merges and execution. Outside contributors may propose tool fixes and metadata, but their PRs and data remain untrusted until reviewed and validated. We no longer require a proof that excludes competing trusted GitHub administrators. Ordinary protection against accidental overlapping jobs, malicious PRs, compromised dependencies, leaked credentials and poisoned data still matters.

This materially revises the earlier Goal 6 deployment assumptions. Its strict original-ZIP interoperability experiment remains parked as a separate research effort, not a prerequisite for useful health updates or a usable CLI. It is neither completed nor silently redefined as passing.

## What basic health means in the first useful release

The default hosted lane is **credential-free with respect to Entra and Nathan's accounts**. GitHub's normal job-scoped platform token/artifact capability is still present; this is not a claim of a token-free process.

The job refreshes the three existing public catalog sources, validates the complete documents, and reports source availability, last successful retrieval, content changes, schema errors, candidate counts, source conflicts and incomplete collection. Checked-in public permission definitions can be inspected as a separate evidence type. A source outage or malformed response preserves the last successful facts and their original dates. It never turns a failed fetch into fresh metadata or absence.

It does not sign in, probe tokens, enumerate private tenant inventory/sign-ins, register applications, grant consent, run Deep/Auto research, or upload private checkpoints. Those are different operations, even when an old workflow calls them shallow discovery. Future account-specific health can be added as a separately approved narrow profile if it is actually useful; it is not assumed in this first lane.

The workstation owns private collection: account/tenant inventory, selected token/API checks, deep callback/protocol exploration, frozen cohorts, exact-plan resume, private comparisons and durable backups. Existing authorization and session-renewal boundaries remain explicit. A long-running research job must not need an assistant or Actions controller polling it. The next acceptance scope remains the existing supported Linux x64 package; verify Nathan's actual execution environment before running anything there, rather than implying an unspecified workstation platform has already passed.

## Minimal deployment

**Runner:** a standard GitHub-hosted Ubuntu VM, one job, no matrix, no persistent workstation runner. GitHub documents fresh instances for standard VM jobs and maintains their images. That is an appropriate platform trust choice here; byte-for-byte attestation of every OS component is not required. Record the actual image/tool/package versions, pin action commits, use a reviewed matching TokenForge package, and fail clearly on unsupported versions. Do not transplant Goal 6's special Node 24.18.1 pin into an unrelated PowerShell/native metadata job. [GitHub-hosted runners](https://docs.github.com/en/actions/concepts/runners/github-hosted-runners)

A dedicated/self-hosted runner becomes relevant only if a concrete requirement appears, such as private network reachability or an unavailable runtime. None is established for public metadata refresh. Do not attach Nathan's normal workstation as a public-repository Actions runner. GitHub warns that public-fork PRs can execute dangerous code on self-hosted machines. [Self-hosted runner guidance](https://docs.github.com/en/actions/how-tos/manage-runners/self-hosted-runners/add-runners)

**Cadence:** propose once daily, off the hour, after one approved manual trial. A daily schedule is a target, not guaranteed freshness. Scheduled workflows run from the default branch; they can be delayed or dropped and public-repository schedules can disable after inactivity. Expose last successful collection and overdue status in the CLI. Do not compensate with overlapping or unbounded catch-up jobs. [Schedule semantics](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule)

**Initial bounds:** one collection pass, three fixed approved source URLs, at most two attempts per source, 30 seconds per request, and a 10-minute overall job timeout. The implementation must enforce explicit response/output byte and record limits compatible with the existing parsers and measured fixtures, and record their final numeric values in the canary packet. No recursive URL discovery, arbitrary PR-provided URL fetching or automatic expansion to more sources. Start with a 14-day public artifact retention request and one non-overlapping health concurrency group. Budgets include retries; incomplete work is reported, not hidden. These are proposed limits, not current live guarantees.

**Permissions:** default repository token read-only, checkout credentials not persisted, no repository/organization secrets, no identity-token, attestation, package or contents-write permissions for this lane. Use a maintained standard artifact action pinned to a reviewed full commit. Artifact upload uses its normal platform capability, not a hand-written Results/Twirp transport. No settings-toggling controller or always-on supervisor is needed.

## Shared evidence without a shared writable database

Keep **SQLite authoritative on the workstation**, with private state directories and existing transactional writers. Runners and the workstation share the same validated schema and evidence rules, not a concurrently mounted SQLite file. Do not put private databases in Git or copy live WAL databases as ordinary files.

The hosted job produces a small public exchange set: validated metadata, a source/run manifest and a health summary. The manifest records source locations and content hashes, successful collection times, per-source completeness, tool/source revision and the GitHub run identity. Hashes prove payload consistency, not the truth of an upstream claim. Ownership, consent, issuance and API acceptance retain their distinct evidence labels.

A single workstation sync command should find/download a named trusted health run, validate its repository/workflow/event/source context, enforce file/size/schema/privacy limits, verify payload hashes, and import transactionally. Do not accept a PR artifact because its filename looks right or because its manifest claims a trusted source SHA. Check the producing run through GitHub metadata, then validate the data independently. Record and reconcile attempt information where the API exposes it; a manifest's attempt value is not independent proof of the artifact's own attempt. Refuse ambiguous selection without inventing an unavailable platform guarantee. Refuse wrong-repository, fork/PR, wrong-workflow, unsupported-schema, conflicting-ID, corrupt, oversized or unexpected-file inputs before changing the database. Downloaded content is data and must never be executed.

Repeated import is idempotent. Older input cannot overwrite newer facts; failed or partial snapshots cannot erase omitted records; complete empty snapshots have explicit meaning. Preserve origin IDs, observation times, source conflicts and history. Validate the complete incoming public ledger with the public-only validator before import; do not use that validator as a redactor on the mixed private destination, which intentionally contains private origins/history. Respect the existing discovery writer lock and database transactions, waiting or refusing cleanly rather than replacing a live SQLite file. Public metadata updates must not replace the frozen private inventory/cohort/plan; report relevant drift and require an explicit new plan while preserving old checkpoints. A crash either commits the validated import or leaves the prior state intact. Collection completion, transfer completion, import completion and export/publication remain separate statuses.

Artifacts are a **temporary transfer mailbox**, not the database or backup. The workstation retains imported history and immutable source receipts, using SQLite-aware backups. If it stays offline beyond retention, report a collection-history gap and fetch the latest valid snapshot; do not invent the missing observations. A later public `discovery-data` promotion path may add durable public distribution, but is not required to finish this first useful loop and must not acquire write permission accidentally.

The new exchange verifies **payload/member bytes and their schema**, not equality of GitHub's outer service archive with a producer-created ZIP. That is an intentional product contract, separate from Goal 6's original C == downloaded R experiment. Standard artifact tooling handles packaging; the importer still fails on its own hash/validation mismatch. GitHub's documented artifact digest mismatch is a warning, so it must not be the sole acceptance gate. No ZIP leakage experiment is needed. [Artifact behavior](https://docs.github.com/en/actions/tutorials/store-and-share-data)

## Contributions and security that still matter

- Tool PRs: isolated credential-free `pull_request` checks only when Nathan separately enables them. No privileged `pull_request_target` checkout/build/test of contributor code, and no privileged `workflow_run` promotion of an untrusted artifact. Nathan reviews workflow, dependency and script changes before they enter the trusted scheduled revision. Approval to spend PR-check minutes is not an endorsement of metadata or authority to use credentials. [GitHub PR security guidance](https://docs.github.com/en/actions/reference/security/securely-using-pull_request_target)
- Metadata PRs: quarantine proposed claims with contributor/source provenance. Schema validity is necessary, not proof. Reconcile against independently fetched approved sources or explicitly authorized local evidence. Never promote a submitted GUID, scope list or callback into verified ownership, consent or successful authentication. Do not execute submitted files or follow arbitrary claimed evidence URLs automatically.
- Supply chain: full-commit action pins, matching reviewed package/source and dependency locks where supported; updates arrive as reviewed changes. Treat public sources as hostile data. Do not restore executable/dependency caches produced by untrusted PRs into privileged work. [GitHub secure-use guidance](https://docs.github.com/en/actions/reference/security/secure-use)
- Privacy: this repository is public despite having one administrator. Logs and artifacts must be suitable for public readers. Upload an explicit allowlist of public output files, not a workspace glob; no profiles, private SQLite, raw identity responses, tokens, cookies, passkeys or account identifiers. Secret masking is not a substitute for excluding secrets. GitHub permits repository readers to download workflow artifacts. [Artifact access](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/download-workflow-artifacts)
- Residual authority: sole human administration does not mean zero Apps, tokens, automated writers, account compromise or platform risk. Before eventual enablement, inspect the actual workflow permissions and existing relevant automation once, and keep normal account/repository protections. Do not turn this into a demand to prove the absence of every trusted writer. Ordinary locks and expected-parent checks remain useful against accidental races.
- Recovery: public GET failures may retry only within the declared limit. Account-bound issuance unknowns, mutations and ambiguous publication outcomes retain their existing explicit-recovery rules. A repeated read or sync must never silently launch authentication or redo deep research.
