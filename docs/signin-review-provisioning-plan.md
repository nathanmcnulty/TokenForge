## Rollback

Disable this workflow and cancel its active run. Remove only the newly added FIC and the two exact assignments on the staged workload. Recheck that no matching trust or effective assignment remains. Previously issued access tokens can remain usable until expiry, so do not treat removal as instant token invalidation. Remove the writer identity, recipient and reader environment configuration created for this rollout. Preserve the app registration and review issue as evidence. Restore the claim-only workflow through a reviewed PR. If rollback also targets branch rules, remove only this recorded ruleset after restoring the source; re-read other active rules, environments, refs, and access. Leave the catalog branch, unrelated trust relationships, release configuration and proof history intact.

## Separately reviewed directory provisioning follow-up

The directory follow-up stages adjacent UTC-day collection of successful v1.0 **Add service principal** events. The sign-in option still calls `collect` and `issue`. Combined mode calls `collect-directory` and `issue-directory` on the same manual workflow. Both jobs use the same mode. A live dispatch requires separate authorization. Before activating or dispatching it, verify that the existing two granted roles, protected branch, both environments, and the reserved issue are unchanged. No new roles or settings are required for this source change. Its encrypted handoff requires every expected UTC-day segment to reach a terminal page and revalidates the exact segment bounds on the writer. The encrypted coverage records unresolved-row counts without ever substituting object or initiator IDs. It checks both catalog partitions and tags each candidate as sign-in, provisioning, or both. The public issue preserves the exact existing candidate lines and adds only eligible new AppIds with fixed labels. The writer verifies the configured issue number, node ID, and creator before writing. Provider retention and missing AppId coverage remain unknown. Unresolved counts refer to returned rows. Candidate AppIds are deduplicated across windows, pages, and sources. A failed directory page or window suppresses the whole handoff in directory mode. In sign-in labels, **sign-in** means the AppId was observed in a sign-in event, which may have failed. It establishes neither Microsoft ownership nor user or admin consent. Publisher labels come only from the separate exact service-principal lookup and do not establish Microsoft ownership.

## Scheduled rollout

The workflow can run daily at 16:37 UTC, but scheduled jobs skip unless the repository variable `TOKENFORGE_SIGNIN_SCHEDULE_ENABLED` is set to `true`. Manual modes are unchanged. Scheduled runs always use the combined Graph sign-in and directory provisioning mode with an overlapping 48-hour window. Both jobs keep their existing permissions, environments and exact-main restrictions; the one-time directory-validation mode remains manual. Do not configure new Graph roles for this rollout.

Before opting in, verify the existing environment branch rules, read-only roles and intended review issue. Verify the first scheduled run reports completed windows for all five sources and updates the reserved queue only for new candidates. An incomplete run never writes to the issue. To stop scheduled access, unset the variable and cancel any in-progress scheduled run; the manual workflow remains usable.

GitHub can delay or drop scheduled runs. Compare successful coverage windows and use one authorized 30-day manual combined run to backfill a gap that exceeds the rolling window. An empty terminal window proves traversal, not retention. Advanced Hunting and live Sentinel queries are outside this change.
