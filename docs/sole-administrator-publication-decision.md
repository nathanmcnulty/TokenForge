## One practical model

Use a manually invoked, pinned **local publisher**, an independent agent's immutable review report, and **Nathan's authenticated GitHub approval**. No Actions runner, sealer job, deployment supervisor, new signing key, scheduler or service is needed for this local path. Reuse the candidate privacy/content validator, semantic diff, exact-old Git protocol, durable intent and read-only recovery components. Give the existing strict hosted path no bypass flags; use a separately versioned policy mode, `LocalSoleAdministratorV1`, only after this decision is approved.

Proposed destination is the existing `nathanmcnulty/TokenForge` repository, **private visibility required**, on its explicitly selected data ref, with append-only `candidates/<candidate-manifest-sha256>/` content. This is a proposed binding, not a fresh visibility/permission assertion. If that repository is not private, stop and revise the proposal rather than silently select a public destination. The first authorized qualification should use an explicitly named disposable private ref. Ref creation, if needed, must be a separately listed operation in that exact live envelope; it is not an implicit setup permission. No write to main is needed.

The approval channel is the discussion of the focused implementation PR in the same private repository. That PR initially contains only source and sanitized documentation. Its source head is pinned independently of the local data commit: **candidate bytes need not be uploaded to obtain approval**. The data commit, tree, diff, outbound object pack and review packet are prepared locally first. This avoids publishing the candidate to a proposal branch before it is approved.

### Operator sequence

1. From retained evidence, construct a new private immutable candidate and readable diff. Show added/changed/removed observations, evidence type, original observation dates, completeness and unknowns. Include exactly the permitted export files; exclude raw stores, claims, tokens, account/tenant IDs, private inventories, logs and paths. No collection or authentication is part of this operation. A privacy schema is not general DLP: the operator and reviewer inspect the exact proposed content.
2. Freeze the source/package/tool identities, original evidence manifest, candidate bytes and per-file SHA-256/length inventory, destination, observed parent, proposed Git tree/commit and exact outbound object-pack digest. Preserve every unrelated path/mode/blob. Independently parse/unpack the exact outbound pack offline: require a bounded non-thin, no-delta profile, verify every object ID and payload digest, reconstruct the fixed canonical pack encoding from the approved objects and compare all original bytes, and admit only the minimal new commit/tree/blob closure needed for this proposed update. Unpacking alone is not complete container/privacy validation. Reject surplus/unreferenced objects, alternate commits, extra tree names/modes, gaps/trailers or opaque data outside the defined profile. Review commit author/committer/message metadata and all pack/container bytes as proposed content, not only the seven exported files; bind the complete object inventory to review and approval. A partial, inconsistent or non-meaningful candidate cannot advance to review. Use a typed local-origin receipt; do not invent GitHub run/artifact IDs or imply hosted attestation.
3. An independently invoked agent reviews that exact tuple, semantic diff, validation and privacy. Its report includes source/package/evidence/candidate/destination/parent/proposed-content identities, review invocation identity, disposition and findings. Corrections invalidate the old report. Resolve findings directly and obtain review again only for affected changes. A report, reviewer-name string or synthetic signature grants **no publication authority**.
4. Present Nathan with the exact candidate/diff and live envelope: private destination/ref, source/package, content inventory, account, existing credential use, permissions, read/write/time/body bounds and recovery procedure. Nathan posts the prepared approval body himself through his existing authenticated GitHub session and explicitly instructs this session to proceed with that approval. The agent must not create or edit an authorization comment on his behalf. These are authorization actions, not relaying technical findings between sessions.
5. The local publisher authenticates the comment author and repository/ref/PR bindings, verifies the exact body and independent report, revalidates immediately before dispatch, and durably records intent. It sends only the approved Git objects and an exact-old ref update. After every POST, including a negative report or lost acknowledgment, reconcile by read-only observation before another attempt or final applied/rejected status. Object transfer is itself publication and belongs inside the approved operation; the current empty-pack writer cannot create new candidate objects unchanged.
6. Verify the resulting remote ref, immutable commit/parent/tree, complete candidate membership and **downloaded blob bytes/SHA-256/lengths**, as well as preservation of unrelated entries. A successful POST or matching ref alone is not final content acceptance. Save the verification instant and receipt; do not claim the remote can never change afterward.

The existing expected-old wire protocol is the appropriate primitive: [Git documents old-ID validation before the ref update](https://git-scm.com/docs/gitprotocol-pack). Do not substitute a read followed by REST `force:false`: [that endpoint documents fast-forward behavior, not an expected-parent parameter](https://docs.github.com/en/rest/git/refs). Approval edit evidence uses the [documented IssueComment edit metadata](https://docs.github.com/en/graphql/reference/issues), with exact bytes still pinned independently. These are protocol/design references, not fresh verification of repository settings or an operational approval.

## Exact approval and review binding

Use an exact, versioned canonical approval body, not free-form “approved.” It binds:

- Policy version/hash and unique transaction nonce.
- Repository numeric ID, full name, **private** visibility, destination ref and versioned path mapping.
- Implementation PR ID and exact source head; publisher package/manifest, runtime and helper digest inventory.
- Original collection/evidence-source and compilation/package identities, separate from exporter/publisher identities; private immutable evidence-manifest digest.
- Candidate manifest/archive digest and size, full permitted per-file content inventory digest, proposed tree/commit and outbound pack digest.
- Independent review report digest and invocation reference, with accepted disposition and no unresolved findings.
- Expected old destination commit, proposed commit's parent, and any separately approved initial-ref creation.
- Actual reader/writer credential principal, observed repository role/capability snapshot and authorized credential-use source, separately from approval-comment authorship; no token value.
- Created/not-before/expiry, explicit operation/attempt ceilings and decision `Approved`.

GitHub API author ID/type establishes the approval account. Reject bots, mismatched/unknown fields, hash/content changes, stale source-PR head, stale destination, incomplete comment/tree responses and ambiguous identity. Require exact frozen body bytes and unedited comment evidence: REST creation/update consistency plus authenticated GraphQL `lastEditedAt == null` for the same comment; do not infer absence of edits from equal coarse timestamps alone. If edit metadata is unavailable or contradictory, refuse. The fixed read-only GraphQL query is separately classified/budgeted as a read even though its HTTP method is POST; arbitrary queries/mutations remain forbidden. Use the latest Nathan comment rule conservatively: any later comment by that author supersedes the selected approval. Nathan therefore approves last; agent review and source corrections precede it. A later approval is a new nonce, never an overwrite of prior custody.

Recommend **15-minute approval validity**, using authenticated server time plus bounded local clock skew and one monotonic execution deadline. Review content is frozen, not a permanent permission. Expiry prevents a new dispatch; it does not prevent GET-only reconciliation of a possibly completed dispatch. Withdrawal cannot retract bytes already dispatched or stop a server-side operation already in flight.

Existing GitHub access may be reused only within the separately approved live envelope, in memory or through an already approved credential helper. Do not create a PAT, install a helper, persist/export a new token, log a secret or silently sign in/refresh. Prefer repository-scoped contents write plus metadata/PR read; no Actions, administration, protection, tenant, OIDC or attestation permissions are needed. Bind the actual receive-pack credential principal separately from the comment author: require the same pinned Nathan user ID for this mode, not an App, bot or other account silently returned by a helper. Snapshot current role/credential capability metadata; it is not proof that branch rules will accept a push. Unexpected identity or unreadable required permission evidence refuses; another principal needs a new explicit trust/live decision. The approved bounded write and final readback establish acceptance of that operation, not general effective authority. Discover actual capability/visibility in an explicitly bounded read-only preflight before approving publication; excess capability is disclosed, not treated as additional authorization.

## Durable recovery without recollection

Keep candidate bytes, pack, report, approval snapshot/IDs, source/evidence identities, transaction intent and remote observations together in one private canonical custody root. Flush intent before sending. Preserve initialization markers, locks, budgets, previous failures and backups; never reset/delete/move a journal to retry. Each process invocation loads the same transaction and cumulative attempt charges.

| Observation | Required action |
| --- | --- |
| No dispatch intent; current parent still matches; approval valid | An initial dispatch may proceed within its approved allowance. |
| Proposed commit observed and all content verified | Record `AppliedVerified`; repeated invocation does no write. Lost ACK needs no resend. |
| Another tip descends from proposed commit | Verify ancestry and the approved directory at that tip. Record applied-and-advanced only if exact approved content remains; otherwise conflict. |
| Known rejection and parent unchanged | First reconcile the actual ref and retained proposed objects; keep the exact candidate. Diagnose without collection; retry only under the explicit remaining retry allowance and fresh approval checks. Permission/protection repair is not implicit. |
| Lost ACK / interruption after durable intent | Enter `Unknown`. Confirm the prior local process is terminal, then perform GET-only reconciliation. Never restart merely because observation timed out. |
| Unknown and expected parent remains | Old-parent observation alone cannot rule out publish-and-rewind or a late first request. Conditional retry requires the explicitly accepted no-rewind premise, identical candidate/pack/proposed commit, current unedited approval and a remaining approved dispatch slot. The Git CAS targets exactly the same commit; a late first application must make the competing second update fail or become already-applied, never publish different content. |
| Different parent, tampering, rewind/deletion, lost custody or missing initialized state | Stop. No automatic rebase, reset or resend. Prepare a new parent-bound proposal/approval from retained content if appropriate; never recollect to disguise the old transaction. |

Recommend at most **one initial dispatch and one explicit reconciled retry**, not an HTTP-library retry loop. Both attempts are charged before sending, uncertain attempts remain charged, and the exact live approval must authorize the retry. Without that allowance, recovery is read-only. A rejected ref update does not prove approved objects were never transferred or retained remotely; record object-transfer uncertainty separately and never imply failed publication securely erased remote bytes. This conditional retry is a deliberate proposed change from the current strict writer's one-POST/recovery-only rule; it is not active now.

Private remote verification necessarily needs GitHub read authority. Recovery reuses existing authorized access and never acquires a tenant session or recollects. If that GitHub session is expired/revoked, retain the evidence and stop: offline data cannot prove the current private remote. Do not promise recovery without any valid remote read access or initiate a new sign-in automatically.
