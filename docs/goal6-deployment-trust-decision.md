## Concrete deployment evaluated

The alternative evaluated was one dedicated synthetic-only repository, one operator-provisioned disposable Linux x64 self-hosted runner, and a supervisor outside the job that delivers one signed plan late. This is a design candidate only: no repository, VM, runner registration, key, permission, workflow or delivery channel was created or approved.

GitHub documents that a self-hosted runner requires communication with Actions and that labels/groups route eligible jobs; these are not an authenticated distribution or exclusive-custody mechanism. Its security guidance also treats workflow write access as powerful authority over job secrets. [Runner reference](https://docs.github.com/en/actions/reference/runners/self-hosted-runners), [secure-use reference](https://docs.github.com/en/actions/reference/security/secure-use). The published repository Actions settings endpoint does not document a lease or compare-and-swap precondition; this decision does not infer one. [Actions permissions API](https://docs.github.com/en/rest/actions/permissions#set-github-actions-permissions-for-a-repository).

**Decisive blocker:** the evaluated infrastructure does not supply evidence of GitHub writer exclusion under the retained model. It also leaves distribution and authenticated late-plan delivery unimplemented. These are missing evidence/authority, not a proof that isolation is impossible on GitHub. A sole-operator arrangement might be acceptable after review, but accepting the operator/platform/host trust roots and any residual competing-writer risk must be explicit. Naming Nathan as recovery owner does not establish acceptance or custody.

We therefore do not select that alternative for implementation or silently relax custody to make it appear feasible. The working TokenForge repository stays untouched operationally. Parking avoids paying the provisioning/control cost before the trust decision is settled.

## Both corrections are mandatory in any reopened plan

**M1 — REST compatibility remains unfixed in the frozen source.** A later implementation must add exactly one non-sensitive fixed `User-Agent: TokenForge-Canary/1.0` to the closed GitHub REST profile and require that value in an independent wire oracle. Missing, incorrect and duplicate values must fail; positive metadata/list/download-redirect cases must exercise the header. Apply the same fixed header and negative cases to every future controller REST operation, reconciling documented request/response shapes rather than copying recording-fixture assumptions. Never forward REST bearer authority to blob destinations. Do not add unrelated headers, origins or retry behavior. This is a documented interoperability defect, not an observed live rejection. [GitHub User-Agent requirement](https://docs.github.com/en/rest/using-the-rest-api/getting-started-with-the-rest-api#user-agent).

**L1 — the current producer has a timeout request, not guaranteed termination within 20 seconds.** The existing `spawnSync` call requests SIGTERM after 20 seconds and can continue waiting if the child does not exit. Current readiness wording is corrected accordingly; no termination implementation changed. [Pinned Node behavior](https://github.com/nodejs/node/blob/9623d9ad85d37d2f0610ec4a82b48182cf2c6061/doc/api/child_process.md#L1374-L1410).

If live integration is reopened, the chosen Linux execution design must place the producer and descendants in supervisor-owned process custody with a monotonic deadline and forced termination, and prevent credential use until confirmed child/custody cleanup and approval revalidation. Validate a SIGTERM-ignoring child, descendant survival, interrupted cleanup, expired authorization and failed termination using synthetic processes without credentials. A signal request, even SIGKILL, is not a real-time OS scheduling/reaping guarantee: the supervisor must enforce process custody independently of the blocked Node thread. A hung `spawnSync` cannot run an in-process deadline handler; if control returns, confirmed cleanup and fresh producer-deadline/approval validation must precede application credential reads/exchanges. Deadline or cleanup failure remains unknown/recovery-required for the supervisor/recovery owner. Preserve the producer's cleared environment and absence of role credentials; supervisor custody does not retroactively revoke platform-injected credentials. Do not claim a 20-second hard wall bound or detach children that can continue using authority.

The independent reviewer agreed that the isolated-runner sketch does not solve customer-controlled GitHub writer exclusion and that neither correction should be marked implemented by this design decision.

## One prerequisite packet to reopen, not a series of coding tasks

Reopening requires one reviewed, concrete deployment/trust packet: the chosen repository and custodian's explicit acceptance; selected image/runtime provenance and provisioning procedure; registered workflow/source strategy; authenticated job/backend identity and late-plan delivery procedure; complete competing-writer inventory and demonstrable exclusion, **or an explicitly approved revision of that requirement**; exact credential roles/scopes; and named recovery responsibilities. If no acceptable mechanism or explicit trust revision is available, leave integration parked.

Design acceptance would still not authorize resource creation, signer provisioning, authentication, settings changes, real HTTPS, dispatch or activation. A separately approved engineering package would then bundle M1, L1, the missing real controller leaf/real response contracts, complete source/runtime/plan binding and independent exact-package validation. Only after that can a separate live decision name the exact source, credentials, destinations, writes, compute, retention and recovery approval. Do not request live approval for current source.

Preserve the existing proposed ceilings if reopened: one synthetic original C <=64 KiB, C == uploaded bytes == R, one-day requested retention, artifact 12 attempts/four mutations/eight reads/180 seconds, controller 30 attempts/six writes/480 seconds and one five-minute Linux job. Reconcile actual deadline/termination custody before claiming these as completed live guarantees. No budget enlargement, tenant change or operational emission is authorized.
