# Manual sign-in review activation candidate

The [workflow reference](../examples/signin-review/activation.yml) mirrors the manual workflow under `.github/workflows`. The separately authorized rollout and the combined run procedure are recorded in the [provisioning plan](signin-review-provisioning-plan.md).

The audit job runs only on exact `main` and has `contents: read` and `id-token: write`. It verifies the separately reviewed `entra-audit` OIDC subject and uses the single-purpose app. The workload assertion and Graph access token stay in process memory. The bearer requests use fixed official GitHub, Entra, and Microsoft Graph endpoints and reject HTTP redirects. There is no Azure CLI login or cache. [Microsoft federated client credentials](https://learn.microsoft.com/en-us/entra/identity-platform/v2-oauth2-client-creds-grant-flow#third-case-access-token-request-with-a-federated-credential) The reader fixes the catalog commit in reviewed source. It passes only fixed-size ciphertext through `needs.collect.outputs.ciphertext`. It computes the normalized candidate envelope in memory without a plaintext runner file or candidate counters in workflow output.

The issue job obtains exact workflow source from the public repository without checkout credentials and has only `issues: write`. A separate writer environment holds the dedicated decryption identity. It verifies source identity and run attempt from its own trusted GitHub context. Workflow concurrency serializes this bot only. Reserve the issue body for the bot and keep manual or other automation edits out of that body. The writer opens only the configured issue number and node ID with the trusted creator and queue marker, and changes only its reserved ID list. The writer has no OIDC permission. Restart all jobs after an incomplete run, so the attempt binding remains valid.

The inaugural manual run requests 30 days separately for interactive user, non-interactive user, service principal, and managed identity events through the beta endpoint. `AuditLog.Read.All` is the documented least application permission. The whole handoff stops if a requested category cannot complete. A fixed category name and numeric HTTP status, when available, identify the failure. A terminal traversal records only the requested windows. [Microsoft Graph beta sign-ins](https://learn.microsoft.com/en-us/graph/api/signin-list?view=graph-rest-beta) Provider retention is unknown. The workflow makes no catalog changes. Combined mode emits a coverage table with fixed status labels, and the encrypted handoff carries the candidate data to the issue writer. The workload's exact proposed Microsoft Graph application roles are `AuditLog.Read.All` (`b0afded3-3588-46d8-8b3d-9842eff778da`) and `Application.Read.All` (`9a5d68dd-52b0-4cc2-bd40-abcf44ac3a30`). A separately verified, existing authorized operator context must update only the new app's required permissions declaration before the later consent phase. Read back the declared roles and effective app-role assignments independently. The workload does not request directory-read, registration, or other write permissions. [Graph permissions](https://learn.microsoft.com/en-us/graph/permissions-reference#applicationreadall)

After both catalog partitions are applied, the reader queries each remaining AppId using the exact Graph v1.0 alternate key and a fixed field projection. An exact 404 creates an unknown label. Transport and permission failures stop the handoff. A documented `AzureADMyOrg` audience excludes the candidate. Local managed identities or legacy principals require explicit type and consistent evidence to exclude. Same-owner status alone never excludes an AppId. The public issue body contains normalized AppIds and fixed source, supported audience, and publisher verification labels. No raw directory labels or values are copied.
