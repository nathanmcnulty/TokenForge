## Controller implementation and its hard boundary

`TokenForgeCanaryControl.mjs` implements the bounded state machine, exact request/response profile, durable intent/charge journal, unique run discovery, cancellation and restoration. Its backend is a private WeakMap-branded **network-free recording fixture**. That backend genuinely excludes competing fixture writers. A boolean, local file lock, signed message or workflow concurrency group never establishes equivalent GitHub authority.

The fixed limits remain 30 attempts, six writes, 480 seconds, ten seconds/request and 1 MiB/control body. Twenty-nine operation slots are assigned; the spare is not a retry pool. Initial checks/enables complete by 80 seconds, dispatch/discovery by 100, polling by 350, cancellation checks by 380 and restoration by 440, leaving 40 seconds before the outer deadline. All responses reserve their full maximum body allowance; errors do not refund slots or reset deadlines. Intents and charges are fsynced before effects. Lost enable/dispatch/restore acknowledgements remain unknown; dispatch never repeats. Zero/multiple/paginated or mismatching run candidates do not authorize guessing or cancellation.

Restoration writes only original enablement bits, after current state/policy checks under the fixture's actual exclusive custody. Lost restore acknowledgements are verified without resending. Interrupted cancellation and clock rollback now durably return named-operator recovery, not a false resolved result or an uncaught final timing error. `Restored` means enablement was verified; unresolved run outcomes remain separately visible. Recovery requires the same in-memory branded authority, source/runtime closure and fixed budget. Fresh-process/backend recovery, stale-lock takeover, cross-job reconstruction and power-loss proof are absent.

**The external controller HTTPS leaf is absent.** Enforceable exclusion of GitHub settings/ref/dispatch/rerun writers has not been established, and the APIs provide no documented lease/CAS guarantee. Adding HTTP calls or removing gates would not solve that prerequisite. This is a precise feasibility boundary for the requested full execution closure, not a claim that recording success completes it. Do not call the package a live-ready controller or a gate-flip deployment.
